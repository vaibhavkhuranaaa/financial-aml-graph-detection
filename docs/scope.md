# Scope

## What it does

Signal Ledger's portfolio product is a read-only public evidence replay over six
bounded realistic synthetic banking cases. A reviewer can inspect sequence,
counterparties, evidence, limitations, and the shape of a simulated human record
without sending a decision to the server.

The project writes its own Bank Secrecy Act typology rules engine to generate the
alert population, so rules only alert volume and per typology recall is the
baseline any ranker has to beat. The headline number is false positive reduction
at held typology recall, reported in alerts and in analyst hours.

The wider research question is alert triage. Its stakeholder is an investigation
lead with a fixed number of analyst hours per daily review period, and its
decision is which alerts get worked first. This work supplies the portfolio
product's evidence and does not change the public data scope.

The triage workbench itself is deployed: a capacity control in analyst hours, a
cut line drawn inside the queue with every alert below it still open and
workable, the queue reorderable to any rung or to the challenger in place,
narrowable by typology and by disposition status without changing a position or
a capacity number, alert detail down to the contributing transactions, a local
only export of the review record, and both the structural zero and baseline wins
states rendered at full weight. It ran locally until the owner recorded a
distribution decision for the triage slice, which covers one review period of the
HI-Small variant and nothing else.

The triage pipeline is complete and runs locally only; the deployed function
imports none of it. The rules engine, the alert store, the alert level feature
build, the backtest harness and the learned ranker exist and are measured. At 126
alerts worked per period across
seven evaluation periods, alert amount descending finds 135 true positives in the
882 worked alerts, rules only priority finds 133, and the learned ranker finds
168. The ranker beats every rung and its lift over the strongest one is 1.2444
against a gate of 1.3, so no model is promoted and the deliverable is the rules
engine, the ladder and the measured negative.

The same pipeline was rerun on the low prevalence LI-Small variant with the
parameter set, the operating point and every metric definition unchanged. The
strongest rung there is chronological rather than amount descending, and measured
against it the ranker's lift is 1.0704 with an interval of 0.9139 to 1.2441. That
interval contains one, so on the low prevalence variant the ranker is not
distinguishable from working the queue in arrival order. It also falls 10.00
recall points below rules only priority on two supported typologies against a
permitted 5, so on that variant it misses two ship criteria rather than one. The
negative is not an artifact of one dataset's prevalence.

## What it deliberately does not do

- It does not suppress, close, or dispose of an alert. It reorders a queue. Every
  disposition is recorded by a human with a rationale.
- It does not draft or file a suspicious activity report, and it never takes an
  action against any party.
- It does not use real customer data. The data is realistic synthetic banking
  data produced by a simulator, and is never described as anonymised customer
  data.
- It does not detect money laundering in the world. It finds transactions
  matching written typology rules inside a simulation.
- It does not perform sanctions screening or customer risk rating.
- It does not score anything at request time. The public surface serves a
  precomputed artifact and accepts no visitor supplied input for scoring.
- It does not publish the larger triage artifact or expose a triage queue on the
  default public surface.
- It publishes what its typology rules mean, not the exact tuned trigger
  thresholds, because a precise trigger set published openly reads as an evasion
  guide.

## Assumptions

- An investigation lead's real constraint is analyst hours, not detection
  coverage. The buying decision is queue capacity.
- Alerts, not transactions, are the unit an analyst opens, so ranking has to
  happen at the alert level to stay operationally meaningful.
- A reordered queue worked top down under a fixed hour budget already has an
  implicit cut line, so reordering alone carries the capacity argument without
  needing suppression.
- Rules parameterised to a plausible target alert volume, rather than to the
  laundering label, are a fair representation of what an institution runs.

## Known limitations

- The laundering flag is generated by a simulator. Every measurement is a
  statement about the simulated population, not about real world detection
  performance.
- The simulator only produces the typologies its authors implemented. A rule
  targeting a pattern it never generates will show a structural zero in per
  typology recall. That is a property of the data, not a model result.
- There is no analyst disposition history, no suspicious activity report outcome,
  no know your customer data and no customer risk rating in the source. Anything
  a production system would learn from investigator feedback has to be
  constructed here, and where it is constructed the write up says so.
- No compliance suitability, regulatory acceptance, or production readiness is
  claimed. This is not a Bank Secrecy Act compliant system.
- Every measured number is a statement about the two Small variants of one
  simulator's output. The prevalence sensitivity run spans a transaction level
  laundering rate of 0.056 to 0.101 percent, and nothing is claimed outside that
  range. No Medium or Large variant has been run.
- The sensitivity run varies prevalence and queue depth together. The rule
  parameters are held fixed across variants rather than retuned to equalise alert
  volume, so the lower prevalence variant also presents a deeper queue at the
  same fixed K.

## How it would scale

The demo topology is a static React build plus one FastAPI function serving a
precomputed bounded artifact on a free tier. It scales with the provider's edge
cache because it does no work per request, and that property is deliberate rather
than incidental.

The path to a larger dataset variant runs through the rules engine, which is the
first component to break, because it holds counterparty windows in memory. Past
the Small variants it moves to partitioned columnar storage and out of core
processing, run once for evidence and torn down inside the recorded cost ceiling.

Selecting a Large variant would make this a data engineering project as much as a
data science one, and that trade is recorded rather than taken quietly.

The serving path does not change at any scale. Putting inference behind a public
URL is a claims decision, not a capacity one, and the answer is no.

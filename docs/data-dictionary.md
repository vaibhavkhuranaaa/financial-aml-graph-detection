# Data dictionary

## Source

IBM AML-Data v8, published by IBM and Erik Altman, distributed on Kaggle under
the Community Data License Agreement, Sharing, Version 1.0. The dataset is
realistic synthetic banking data generated by a simulator. It is not anonymised
customer data and contains no real person or organisation.

- Grain: one row per transaction.
- Variants retrieved and verified: `HI-Small_Trans.csv`, roughly five million
  transactions, which is the alert triage evaluation variant and the source of
  the bounded public fixture; and `LI-Small_Trans.csv`, roughly seven million,
  used for the prevalence sensitivity run and local only. Both carry their own
  source manifest under `data/provenance/`.
- Period: as published by the generator; static release, version 8.
- Refresh cadence: none. It is a fixed release.
- Obtaining it: the Kaggle dataset
  `ealtman2019/ibm-transactions-for-anti-money-laundering-aml`, version 8.
  Retrieval requires an authenticated Kaggle account and acceptance of the
  dataset terms. Raw files are never committed to this repository and never
  served.

The only committed data is `data/fixtures/public_casefile.json`, a bounded six
case, 55 transaction replay artifact reproduced deterministically from a verified
local source manifest and an approved distribution decision. Source and artifact
checksums are recorded in the private delivery records rather than here.

## Fields

Source transaction file. The published header repeats `Account` positionally; a
naive header based read silently drops one of the two.

| Field | Type | Meaning | Nullable | Notes |
| --- | --- | --- | --- | --- |
| Timestamp | datetime | When the transaction occurred | no | Ordering key for every time based split |
| From Bank | integer | Originating institution identifier | no | |
| Account (first) | string | Originating account identifier | no | First of the two positional `Account` columns; mapped to from account |
| To Bank | integer | Beneficiary institution identifier | no | |
| Account (second) | string | Beneficiary account identifier | no | Second positional `Account` column; mapped to to account |
| Amount Received | decimal | Amount credited to the beneficiary | no | In the receiving currency |
| Receiving Currency | string | Currency of the credit | no | |
| Amount Paid | decimal | Amount debited from the originator | no | In the payment currency |
| Payment Currency | string | Currency of the debit | no | Differs from receiving currency on cross currency movement |
| Payment Format | string | Rail or instrument used | no | |
| Is Laundering | integer | Simulator flag, 1 when the transaction is part of a generated laundering pattern | no | Ground truth for the simulation only |

## Derived fields

Planned. None of the alert layer is built yet, and this table is filled as it is
implemented.

| Field | Built from | Rule | Used by |
| --- | --- | --- | --- |
| alert_id | subject account, period, fired rules | Stable identifier for one alert | Alert store, queue, evaluation |
| subject_account | transaction account fields | The account the alert is raised on | Alert store |
| alert_period | Timestamp | The window the alert covers | Feature cutoff, time based split |
| fired_rules | rules engine | Set of typology rules that triggered, R1 to R8 | Per typology recall, queue display |
| trigger_evidence | rules engine | Per rule, the transactions and measurements that fired it | Alert detail, explanation |
| alert_label | Is Laundering over the alert window | Whether the alert resolves as suspicious in the simulation | Evaluation target |
| feature_cutoff | alert_period | The timestamp beyond which no feature may read | Leakage gate |

The evaluation target is the alert label, not the raw transaction flag. Alerts
are the unit of analysis because alerts are what an analyst opens.

## Quality controls

Implemented today:

- Schema and contract tests on the public API and the replay artifact.
- A checksum gate that refuses to serve an artifact whose recorded hash does not
  match its bytes, or whose source manifest is unverified, or whose distribution
  decision is unapproved.
- Deterministic rebuild: the fixture builder must reproduce the committed
  artifact byte for byte from the same verified source.
- A public boundary test asserting the absence of write routes and local only
  research paths.

Planned with the alert layer:

- Duplicate and range checks on the transaction load, with the positional
  `Account` duplication asserted rather than assumed.
- A base rate record for every typology rule before it enters the alert
  population.
- A leakage gate that fails the build if any feature reads a transaction dated
  after its declared cutoff.
- Time based split enforcement, with random splits rejected in test.
